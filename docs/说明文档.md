## 整体介绍

GICI Data Packer 是一个用于将 GNSS 观测数据、IMU 数据和图像数据打包成**GICI可运行的 ROS bag 文件**的工具。支持**处理 RINEX 3.04 格式的 GNSS 观测文件和导航文件**，以及 IMU 数据和视频数据，将它们转换为 ROS 消息并保存到 bag 文件中，以便于后续使用 GICI 处理。

本项目为个人学习实践代码，基于特定环境与示例数据编写，未经全面测试，可能存在疏漏，仅供学习参考，敬请谅解。

在这里讲解主要自己的设计思路，和分享**编写代码过程中的学习笔记**。

### 项目结构

项目采用了典型的 ROS 包结构，主要包含以下部分：

- `include/`：包含所有头文件，定义了数据结构和函数接口
- `src/`：包含源代码实现
- `gici_msg/` 和 `gvins_msg/`：包含自定义的 ROS 消息类型
- `CMakeLists.txt` 和 `package.xml`：ROS 包配置文件

### ROS系统

本项目基于 Ubuntu 20.04 + ROS Kinetic 开发（使用 GICI 运行也是这个环境），推荐使用`catkin_make`编译。

**自定义消息**：为 GNSS 数据定义了专门的消息类型，如 `GnssObservations`、`GnssEphemerides` 等

因为使用了自定义消息，所有`*.msg`文件都要先编译一遍才能使用，必须在 ROS 工作空间中按 ROS 项目规范配置。即建立工作空间目录(`_ws`)，在`src`目录下放入源码。

### 主要难点

1. **原始观测值转换处理**：因为RINEX文件的原始观测值与GICI消息**并不完全等价**，所以需要进行少量的转换操作。
2. **异常情况处理**：需要对异常情况进行妥善处理，例如当某频率的观测值为空。
3. **时间系统转换**：需要**尽可能统一以GPST为基准**，然后再将其转换为BDT、UTC、Unix时间等其他时间系统。

## IMU和图像的转换

### IMU 数据处理

IMU 数据处理模块的主要功能是读取 CSV 格式的 IMU 数据，并将其转换为 ROS 的 `sensor_msgs/Imu` 消息，**写入 Bag 文件中的`/gici/imu_raw`话题**。

**实现思路**：

1. **数据读取**：使用 `IMUIterator` 结构体管理文件读取位置和当前数据
2. **数据解析**：从 CSV 文件中读取时间戳、加速度和角速度数据
3. **消息转换**：将解析的数据填充到 `sensor_msgs/Imu` 消息中
4. **时间戳处理**：直接使用 CSV 文件中的时间戳作为 ROS 消息的时间戳

### 图像数据处理

图像数据处理模块的主要功能是读取视频文件和对应的时间戳文件，将视频帧转换为 ROS 的 `sensor_msgs/Image` 消息，**写入 Bag 文件中的`/gici/image_raw`话题**。

**实现思路**：

1. **数据读取**：使用 `ImageIterator` 结构体管理视频文件和时间戳文件的读取
2. **视频处理**：使用 OpenCV 的 `VideoCapture` 读取**视频帧图像**
3. **时间戳同步**：从 CSV 文件中读取**每个帧的时间戳**
4. **消息转换**：将视频帧和时间戳信息填充到 `sensor_msgs/Image` 消息中

## GNSS部分

**GVINS 提供了 gnss\_comm 库**，能方便地实现 GNSS 原始观测数据的转换。不过，GICI 与 GVINS 存在诸多差异，因此不得不重新编写代码实现**原始观测 → GICI 的 GNSS 消息**，编写过程中部分代码参考了 gnss\_comm 库。

### 整体思路

星历和观测值分别打包进入**不同的bag文件**（先这样做，这样更简单，之后考虑转换为单个bag文件）

1. 先完整打包观测值，并且得到每个观测历元的列表，**得到 obs.bag 文件**
2. 遍历每个时间戳，每50个（或者自定义数量间隔），加入一次星历消息
3. 找到该时间戳对应的**每一颗卫星**（不考虑该卫星在**观测值卫星列表**中是否存在）的最新星历

#### 相关变量和结构体

这里没有详细说明，仅仅简要概况，具体变量、结构体内容见源码中 constant.hpp

- **结构体设计**：仅保留观测值（obs）、星历基类（GCE/R）与时间（gtime\_t）三个核心类，确保与ROS消息格式严格对齐。
- **常量体系**：完全沿袭RTKLIB的频率常量与数字系统标识（如SYS\_GPS），通过字符映射表兼顾底层算法兼容性与代码可读性。
- **卫星编号**：参考gnss\_comm方案，显式定义各系统PRN上限（如北斗1-63），简化卫星编号映射逻辑并预留扩容空间。

### 观测值转换

1. \*\*文件头解析：\*\*获取每个卫星系统（GPS、GLONASS、Galileo、BeiDou）对应的观测值类型列表，比如GPS对应`C1C L1C D1C S1C C2S L2S D2S S2S`
2. **单历元观测数据解析**：
   1. 读取这一时刻的观测时间，和该历元观测值个数
   2. 遍历每个观测值行，解析卫星 PRN 码、伪距、载波相位、多普勒和信噪比等数据
3. 将这一历元的观测值列表转换为消息，写入bag文件

#### 注意事项

- 对信噪比数据进行单位转换（乘以 1000）（信噪比单位错误，导致所有观测值都因为噪声太大被拒绝）
- 多普勒观测需要**取负**，单位不用转换（多普勒观测值错误，导致初始速度极大）
- 过滤掉无效的观测值
- 将 GPST 时间转换为 Unix 时间戳，用于 ROS 消息的时间戳
- 计算周数和周内秒，GICI 的消息要求使用周+周内秒，注意统一使用GPST

#### 空缺观测值的处理

读取的过程中，如果中间的观测值缺失是一个非常大的问题。因为**不同格式的观测文件**（不同软件/接收机生成的**同一版本的RINEX文件**），对空缺观测值的处理也是不一样的。

1. 某频率的4个观测值要么同时出现，要么同时空缺
2. 某频率4个观测值中间存在一个空缺，是纯空格
3. 某频率4个观测值中间存在一个空缺，使用00000填充

一旦出现**频率列表**和**观测值列表**出现错位，后果非常严重。

**最终确定的解决方法是：**

1. 遍历每一个频率，也就是`观测值类型个数/4`
2. 如果这个频率4个观测值全部为空，直接跳过。**该频率直接不加入`code`列表**
3. 只要存在1个不为空，则4个观测值全部填入变量，空缺值填0。并且将该频率加入`code`列表。

`ObsPtr obs = std::make_shared<Obs>();` **指针一定要记得初始化，分配内存！**

### 星历转换

具体对星历每个数据的处理详见代码，各系统的星历结构都有所不同。

1. **星历数据解析**：
   - 对于 GPS、Galileo 和 BeiDou 卫星，解析 8 行星历数据
   - 对于 GLONASS 卫星，解析 4 行星历数据
   - 提取星历参数，如轨道参数、钟差参数、健康状态等
2. **星历选择策略**：
   - 根据观测时间选择最合适的星历数据
   - 选择在观测时间之前发布且距离观测时间最近的星历
3. **消息转换与组装**：将解析的星历数据转换为对应的 ROS 消息类型

#### 注意事项

- 确保选择的星历在观测时间之前发布，并且最新
- **一定要注意时间系统的转换，如果GICI解算大量出错，大概率是时间系统的错误**
- 星历的具体格式需要去读RINEX文档
- 导航文件中记录了闰秒的总次数，但是我已经提前写在常量里面了。所以省去这一步读取。

## 时间系统处理

本程序一切使用GPST为转换基准。

时间系统的问题，不能全听AI的，AI说的是可能错的。

### 了解各时间系统

- **协调世界时 (UTC)**：有“**闰秒**”（下述各系统**全部没有闰秒**）
- **GPS时间 (GPST)**：1980年1月6日零点开始（与这一时刻UTC对齐），不闰秒，**表示形式**有：纯秒数、GPS周+周内秒、年月日时分秒
- **北斗时间 (BDT)**：起点为2006年1月1日（与这一时刻UTC对齐），与GPST保持固定的周和秒偏差（1356周和14秒），这14秒其实是1980\~2006年期间的闰秒，所以已经固定。
- **伽利略时间 (GST)**：起点为1999年8月22日
- **Unix时间**：自1970年1月1日起，不闰秒（这是计算机中统一使用的时间）

#### 闰秒

理论上存在正闰秒和负闰秒，但实际上负闰秒从来没有出现过，**50年来全部都是正闰秒**。

正闰秒会使UTC出现“短暂停顿”（通常是将这一秒分散在数十个小时中进行**稀释**）。而在闰秒时刻，**GPST仍正常推进**，这就导致由GPST转换得到的**年月日时分秒**比UTC时间**快几秒**。

**记住GPS比UTC时间快18秒**，即在1980年后一共经历了18次闰秒。（在1980\~2026年之间的闰秒总数上，不同AI回答的也不一样，所以这个不要相信AI。）

### 各系统转换关系

截至2026年，各个时间系统之间的差别如下

- GPST = UTC + 18 秒
- BDT = UTC + 4 秒
- GPST = BDT + 14 + 3600\*24\*7\*1356秒
- GPST周内秒 = BDT周内秒 + 14 秒
- GPST整周数 = BDT整周数 + **1356周**
- Galileo整周数 = GPST整周数 - 1024周（**周内秒对齐一致**）
- Unix时间=GPST+315964800秒（**3657天**，Unix时间提前10年）

UTC时间没有如“1970年1月1日”这样的明确起点，不能用总秒数表示，因此可通过加减闰秒与BDT、GPST进行转换。而GPST和BDT有明确的时间起点，能用总秒数计时，二者的转换关系可通过总秒数的加减来获得。

#### 伽利略时间 GST

GALILEO也有自己的时间起点，那么伽利略系统如何处理了1980到1999年的闰秒？为什么可以对齐？

**直接从 1999 年开始定义自己的连续原子时，并与当时的 GPST 对齐。因此，它天然避开了历史闰秒问题。**

#### 奇怪的 gpst2unix

**ROS 消息**中使用的时间系统是**Unix时间**，那么和GPST之间的转换应该**不用考虑闰秒**，只要考虑两者的**时间起点的差距**。

可能是因为**IMU/视频数据**使用的就是**UTC时间**，所以如果我不考虑闰秒把GPST转换为Unix时间，会导致IMU/图像数据与GNSS的时间戳差18秒，这里**又减去了闰秒**。所以这里实际上是以1970年1月1日为起点的，仅仅考虑了1980~2026年间闰秒（而没有考虑1970~1980的闰秒）的**某个混合时间系统**。

**好奇怪呀，我并不理解，但这样的确是可以正确运行**。如果出现了问题，比如**VI数据**与**GNSS数据**时间存在18秒偏移，可以**首先怀疑这个函数是否存在问题**⭐⭐。

#### 解析年月日时分秒 epoch\_array2gpst

将**年月日时分秒**转换为以**1970年1月1日为基准**的总秒数，**中间并没有考虑闰秒**。这应该是RTKLIB提供的**间隔天数的计算逻辑**，很巧妙。

```C++
days = (year-1970)*365 + (year-1969)/4 + doy[mon-1] + day-2 + (year%4==0&&mon>=3?1:0)
```

在这个基础上**减去3657**就相当于将天数转换到**1980年1月6日起点**。于是得到了**时间戳**转换来的**GPST基准下的总秒数**。

注意！这个函数计算的是**连续的时间差值**，转换为总秒数是以1980年起点的。如果年月日时间戳本身是BDT：

- 需要得到BDT的总秒数：只需要补充26年间的差值（3600*24*7\*1356），**并不用考虑闰秒**。因为补上了日期差异，就是当前时刻与2006年1月1日之间的总秒数。
- 需要得到GPST的总秒数：时间戳本身是BDT，需要+14秒再转换得到的是正确GPST总秒数。在调用了`epoch_array2gpst`之后，对总秒数+14，可以转换为GPST基准下的总秒数。

#### 将总秒数转换为周+周内秒

这里不用区分不同卫星系统的时间起点，统一使用GPST作为基准。

- 整周数都是从1980-1-6开始计时，不用考虑北斗、GALILEO的时间起点。
- 周内秒统一以GPST为基准，不需要考虑北斗的偏移。

#### BDS 的勘误

在官方文档中发现了一句勘误：

> Corrected A5 – W Reference week number by removing BDS from the group in parentheses so that it is clear that BDS week starts on 1-Jan-2006, as week zero.

这是**针对附录 A5 的一条具体勘误说明：**
修正了 A5 – W 参考周数：把 BDS 从一个括号里的系统列表中删除了，是明确北斗（BDS）自己的周计数起点与其他系统不同。

#### 附录A5部分（BDS周数）

接下来仔细阅读**附录A5部分**，标题是：GNSS Navigation Message File – Header Section Description，也就是对**导航文件的文件头**的讲解。

在A21页，出现了一句解释，**BDS从2006开始计算周数**。GPS、GALILEO从1980年开始计数，这个括号中，**没有包含BDT**。

> W Reference week number (GPS/GAL/QZS/IRN/SBAS week, continuous number from 6-Jan-1980), T and W zero for GLONASS. BDS week, continuous from: 1-Jan-2006

#### 周内秒的基准

此外，还提到：各卫星系统相对于**自己周起始时刻**的秒数计算方式是一样的（除了GLONASS）

> T Reference time for polynomial (Seconds into GPS/GAL/BDS/QZS/IRN/SBAS week)

北斗卫星在 RINEX 文件中记录的周内秒是相对于 **BDS 周起始时刻（周日 00:00:00 BDT）** 的秒数，而非 GPST。**第4行的第1个参数**，在RINEX文件中说的是：**Toe Time of Ephemeris (sec of BDT week)**（页码：A33）

所以RINEX文件中记录 Toe 的**本身就是BDT基准下**的，而不用从GPST转换到BDT。
